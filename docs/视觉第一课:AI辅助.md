# 视觉第一课：AI 辅助

> 本文不展开模型原理，主要介绍 AI 项目协作中的使用方法。

## 1. 基本认识

AI 可以帮助我们理解题目、分析代码、设计算法、解释报错、补充测试和阅读文档，但它的输出不等同于正确答案。使用者仍然需要理解问题、判断方案、运行代码并对结果负责。

在编程中，AI 更适合充当助教、陪练和开发助手，而不是代替思考的“答案生成器”。推荐的基本流程是：

```text
理解问题 → 提供上下文 → 形成方案 → 编写代码 → 运行测试 → 根据结果迭代
```

---

## 2. 相关术语的工程化理解

| 术语 | 在编程中的作用 | 初学者的理解方式 |
| --- | --- | --- |
| LLM | 理解和生成代码、文字及结构化内容 | AI 编程工具的基础模型 |
| Prompt Engineering | 组织任务说明、上下文和输出要求 | 把问题描述清楚 |
| Context Engineering | 组织项目文件、约束、历史信息和验收标准 | 给 AI 准备完整的工作材料 |
| RAG | 根据指定文档检索信息后回答 | 让 AI 参考项目文档或官方资料 |
| Function Call / MCP | 让模型连接搜索、终端、文件等外部工具 | 让 AI 不只回答，还能执行操作 |
| Agent | 分解目标并完成多步任务 | 能够读文件、改代码和运行测试的助手 |
| Skill | 固定某类任务的工作步骤 | 可以反复使用的工作方法 |
| Harness | 组织模型、上下文、工具、权限和反馈的工作环境 | 让 Agent 按规定方式工作 |

可以简单理解为：**模型提供能力，Prompt 和上下文描述任务，工具帮助执行，Harness 组织整个流程，Skill 则把有效方法固定下来。**

## 3. LLM

LLM（Large Language Model，大语言模型）能够根据上下文生成和分析文本。在编程中，它可以解释语法、阅读代码、提出算法思路、生成样例和协助调试。

选择工具时不必过度关注品牌，主要考虑：

- 是否能够处理当前语言、框架和版本；
- 是否支持文件读取、代码执行、测试或文档检索；
- 是否能够提供完整上下文并显示具体修改；
- 是否符合项目的隐私、权限和成本要求。

工具能力越强，越需要关注权限和验证。能够修改文件或执行命令，并不意味着可以不经确认地修改整个项目。

## 4. 提示工程：把问题说清楚

好的提示词不依赖固定格式，但通常应包含以下信息：

```text
目标：要解决什么问题
背景：项目、题目和使用场景
环境：语言、版本、框架和依赖
材料：代码、目录、报错、输入输出和文档
约束：不能改变什么，允许修改什么
输出：希望得到思路、代码、测试还是解释
验收：通过什么现象或测试判断完成
```

提问前应先做必要的检索和尝试，例如查看题目说明、官方文档、项目 README 和已有讨论，并记录已经尝试过的方案。提问时应描述实际症状，不要直接把“某个库有问题”当作结论；同时应说明期望结果，而不要一开始就限定 AI 必须采用某种实现方式。

### 4.1 提示词的基本组成

提示词可以由四部分组成：

- **指令**：要求 AI 完成什么任务；
- **上下文**：项目背景、规则、文档和必要的代码；
- **输入**：具体题目、报错或待处理内容；
- **输出要求**：回答的格式、范围和验收方式。

并非每次都需要写全，但任务越复杂，越需要补充上下文和约束。提问前应先查阅题目说明、README、官方文档和已有讨论，并说明已经尝试过什么。描述实际症状，不要把未经证实的猜测当作结论；同时说明目标，不要过早限定解决方法。

### 4.2 提高提示质量的几个要点

- **从简单开始**：先写出基本要求，根据回答中的问题逐步补充信息；
- **描述具体**：说明语言和版本、输入输出、边界条件、允许修改的范围，避免使用模糊表达；
- **明确输出**：直接说明需要算法思路、代码、测试还是解释，需要固定格式时可以给出示例；
- **拆分复杂任务**：先分析题意和方案，再实现代码，最后进行测试和审查；
- **使用正向要求**：与其只说“不要出错”，不如要求列出假设、标注不确定之处并给出验证方法；
- **持续迭代**：把提示词看作需要测试和修改的工作说明，而不是一次写成的固定答案。

算法题可以要求 AI 先说明问题抽象、关键观察和复杂度，再给出边界案例；代码调试则应提供环境、完整报错、复现步骤、期望结果和最小可复现代码。得到回答后，还可以要求 AI 解释方案、构造反例或列出验证步骤，以检查自己是否真正理解。

一个通用的提问结构如下：

```text
目标：【要解决的问题】
背景与环境：【项目、语言、版本和相关文档】
输入材料：【题目、代码、报错或运行结果】
约束：【不可改变的接口、文件范围和其他限制】
输出要求：【思路、代码、测试或解释】
请区分已确认事实和推测，并给出验证方法。
```

## 5. Harness：为 AI 准备工作环境

Harness 可以看作一种工程化使用 AI 的思想：通过明确任务范围、补充必要上下文、控制工具权限并提供反馈机制，让 AI 在可验证的环境中稳定完成工作。

一个适合编程任务的 Harness 通常包括：

- **上下文**：项目文件、README、接口文档和历史信息；
- **指令**：任务目标、编码规范、执行步骤和输出要求；
- **工具**：文件、终端、测试、搜索和版本控制；
- **权限**：允许访问和修改的范围；
- **反馈**：编译结果、测试结果、日志和审查意见；
- **验收标准**：判断任务是否完成的客观条件。

模型提供代码理解和生成能力，Harness 则决定模型能看到什么、能使用什么工具、应当按照什么步骤工作，以及如何根据结果继续调整。**Harness 决定这些能力能否稳定地用于实际工作。**

搭建 Harness 的重点不是增加更多指令，而是提供相关的上下文、明确的权限边界和可观察的反馈。例如：

```text
请修复当前项目中的配置解析问题。
请先阅读相关实现、测试和 README，复现问题后再提出方案。
只修改 config 模块及其测试，不改变公开接口，不新增依赖。
修改后运行相关测试，并报告修改文件、测试结果和剩余风险。
删除文件、修改项目配置或执行发布操作前先向我确认。
```

这样可以减少 AI 脱离项目猜测、无关修改和提前宣布完成的情况。问题解决后记录原因、修改内容和验证结果，还可以将一次性的处理经验沉淀为项目文档或 Skill。

## 6. Agent：让 AI 执行多步任务

普通对话框通常是“提出问题，获得回答”，用户需要自己查找文件、执行命令、复制结果，并决定下一步做什么。Agent 则可以围绕一个目标自主拆分任务，在授权范围内读取文件、调用工具、修改代码、运行测试，并根据反馈继续推进。

相比普通对话框，Agent 的主要优势是：

- **处理连续任务**：不必每一步都由用户手动复制和转述；
- **使用真实环境**：可以基于项目文件、终端输出和测试结果工作，而不是只根据对话片段猜测；
- **形成反馈闭环**：修改后可以主动运行测试，根据结果继续调整；
- **适合项目级任务**：适用于功能实现、错误排查、代码迁移和批量整理等多步骤工作。

Agent 并不等于完全自动化。它的效果仍取决于 Harness 提供的上下文、工具和权限，涉及删除、发布、发送信息或修改重要配置的操作应保留人工确认。一个合适的 Agent 任务应说明目标、范围、保留条件、验证方式和高风险操作的处理规则。

## 7. Skill：固定有效的方法

Skill 是 Harness 中可复用的一组任务说明。它把工作顺序、判断标准和输出格式固定下来，能够减少遗漏，提升回复的一致性和可复查性。相较于一次性的提示词，Skill 更像一套可以反复调用的工作规范。

### 7.1 为什么需要 Skill

Agent 的能力不断增强，但仅凭模型本身，往往仍然缺少可靠完成实际任务所需的背景信息。Skill 可以将领域知识、团队规范和用户习惯，与任务步骤、参考资料和其他资源一起整理成可移植、可版本控制的文件夹，由 Agent 在需要时加载。

Skill 的价值主要体现在三个方面：

- **沉淀领域知识**：将代码规范、数据分析流程、文档格式或项目约定等专业经验整理为可复用的指令和资源；
- **形成可重复的工作流程**：把多步骤任务转化为稳定、可检查、可追溯的操作流程，减少每次重新说明的成本；
- **支持跨产品复用**：Skill 一旦编写完成，就可以在不同的兼容 Agent 中使用，不必针对每个工具重复建立同一套方法。

因此，Skill 不只是提示词的集合，更是 Agent 可以按需加载的知识与工作流程。它使个人经验、团队规范和项目方法得以保存、迭代和共享。

### 7.2 GitHub 案例：Systematic Debugging

GitHub 开源项目 [obra/superpowers](https://github.com/obra/superpowers) 提供了 `systematic-debugging` Skill，用于处理测试失败、运行错误、构建失败和异常行为。

它的核心原则是：**找到根本原因之前，不直接进行修复。** 主要做法是先阅读完整报错并复现问题，收集相关证据；再检查近期变化、对比正常代码；随后提出一个明确假设，一次只验证一个原因；最后进行最小修改并运行测试。

可以将它理解为一套“不要猜，先取证；不要乱改，一次验证一个假设；不要凭感觉完成，必须测试”的调试纪律。

它提高回复质量的原因在于：减少基于表面现象的猜测，控制修改范围，并通过测试形成反馈闭环。Skill 不一定增加模型的知识，但可以改变模型的工作顺序，使输出更加稳定。

使用 Skill 时不必机械照搬全部内容，应保留其中的核心方法，并结合项目的语言、测试框架和权限边界进行调整。Skill 的价值在于把经过验证的经验沉淀为默认工作方式。

参考：[systematic-debugging/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)

## 8. 更进一步:MCP、Agent 分工与自动化

MCP 可以理解为 Agent 连接外部工具的一种方式，例如项目文件、终端、技术文档和版本控制工具。工具不应全部开放，应遵循最小权限原则：只读任务不开放写入权限，只运行测试不开放部署和删除权限。

一个 Agent 足以处理大多数小型任务。项目较大、任务可以独立进行时，才考虑分工，例如由不同 Agent 分别负责需求分析、代码实现、测试和审查。分工必须配合明确的输入、输出和验收标准，否则只会增加沟通成本。

定时任务适合测试汇总、依赖检查和项目记录整理等重复且容易验证的工作。涉及删除、发布、发送信息或修改生产环境的操作，应保留人工确认。

这些能力可以逐步加入工作流，而不必一次性全部配置。先把一个高频、低风险的任务做好，再根据实际需要增加工具、Skill 或 Agent 分工，通常更容易发现问题并形成稳定方法。

问题解决后，应简要记录最终原因、采取的修改和验证结果。这样的记录既方便下次检索，也能逐渐沉淀为项目文档、Skill 或自动化检查。

## 9. 使用边界

- 不要提交自己无法解释的代码；
- 不要将密码、API 密钥、私钥和个人信息提供给不可信工具；
- 不要把未经运行和测试的代码视为完成结果；
- 使用第三方 Skill、MCP 和依赖前，应查看其来源、权限和内容；
- 遵守项目对 AI 使用范围的规定。

---

## 10. 小结

AI 辅助编程可以从简单对话开始，逐步发展为由上下文、工具、权限、Skill 和反馈组成的工程化工作流。算法学习中，应让 AI 帮助理解问题、比较方案和发现反例；项目开发中，应让 AI 在明确范围和可验证环境中完成任务。

最重要的原则是：**先理解，再生成；先验证，再交付。**
